# Public repository IP, privacy, and security boundary

## Non-negotiable rule

This repository may contain only material that is safe and authorized for
public release. Technical usefulness does not override intellectual-property,
privacy, security, customer, employment, or license obligations.

When provenance or permission is unclear, do not add the material. Replace it
with a freshly created minimal reproducer using public or synthetic inputs.

## Allowed material

- Original code and documentation written specifically for this public lab.
- Public open-source code used according to its license, with attribution and
  modifications documented.
- Public model weights whose terms permit the intended use and redistribution,
  or download scripts pointing to the canonical source when redistribution is
  not permitted.
- Public datasets used according to their license/terms, preferably referenced
  by download and subset manifests rather than committed copies.
- Synthetic inputs generated by code in this repository, provided they do not
  recreate or encode private data.
- Small reviewed text excerpts and derived summaries generated solely from the
  above material on a personally authorized environment after redaction review.
  Raw logs and profiler captures remain local/untracked.

## Prohibited material

Do not commit, paste into issues, upload as release artifacts, or embed in
screenshots:

- employer, former-employer, partner, supplier, or customer source code;
- internal patches, build files, configuration, architecture documents,
  tickets, chat, email, dashboards, or copied problem descriptions;
- non-public model architecture, weights, calibration caches, training data,
  labels, maps, routes, rosbag/MCAP files, sensor frames, CAN data, or telemetry;
- vehicle, customer, employee, or test-subject identifiers and location traces;
- internal logs, stack traces, symbols, hostnames, usernames, directory trees,
  IP/MAC addresses, VPN/tailnet details, repository URLs, and service endpoints;
- passwords, API keys, access tokens, cookies, certificates, private keys,
  cloud credentials, SSH material, `.env` files, or secrets in Git history;
- third-party code, papers, figures, weights, or datasets without compatible
  permission, even if they are easy to find online;
- benchmark numbers copied from private/company hardware or workloads;
- confidential details remembered from work and merely paraphrased;
- raw TensorRT engines, ONNX exports, Nsight captures, datasets, or other large
  generated binaries; keep these local and publish only reviewed small derived
  summaries and reproducible commands.

"Anonymized" is not automatically safe. A unique route, tensor shape, customer
failure signature, timestamp, or configuration can re-identify a source.

## Converting real experience into a public reproducer

It is acceptable to study a general mechanism learned through work. The public
artifact must be independently created:

1. State the generic mechanism without copying the original expression or data.
2. Select a public model and public/synthetic input unrelated to the incident.
3. Implement a minimal failure from first principles in this repository.
4. Verify that no distinctive private names, shapes, constants, logs, or system
   topology were carried over.
5. Explain only what the new public evidence demonstrates.

Do not claim that the public reproducer is the same as, fixes, or reports a
private incident.

## Third-party license and asset review

For every dependency, model, checkpoint, and dataset, record:

- canonical source URL and owner;
- exact revision/version and SHA-256 when downloaded;
- license/terms URL and any attribution or redistribution requirements;
- whether the asset is committed, downloaded by the user, or referenced only;
- restrictions on commercial use, derivatives, benchmarks, or generated
  outputs;
- the date terms were reviewed.

Code license, weight license, and dataset terms may differ. If the terms do not
clearly permit public redistribution, commit only a manifest/download
instruction when that is allowed. Legal interpretation belongs to qualified
review, not this repository.

## Secrets and local identifiers

- Use environment variables or local untracked configuration for secrets.
- Examples use placeholders such as `${TOKEN}` and non-routable documentation
  addresses, never realistic credentials.
- Prefer relative paths in logs and reports. Replace user/machine names with
  stable public labels.
- Do not publish complete environment dumps; allowlist relevant fields and
  redact values before artifact creation.
- Treat profiler exports as potentially sensitive because they can include
  command lines, paths, source names, and process metadata.

If a secret is committed, stop publication, revoke/rotate it immediately, and
remove it from history using an approved process. Deleting it in a later commit
does not remove exposure.

## Pre-publication review

Run the checks on the exact staged/release content, then inspect manually:

```bash
git status --short
git diff --cached --stat
git diff --cached
git ls-files
git grep -nEI '(api[_-]?key|access[_-]?token|secret|password|BEGIN (RSA |OPENSSH )?PRIVATE KEY)' -- . ':!docs/public-repository-boundary.md'
```

Automated scans are incomplete. Review binary files, Git LFS pointers, image
metadata, notebooks, traces, archives, generated reports, and Git history.
Never run a cleanup command that would destroy unrelated user work.

### Required release checklist

- [ ] Every model, weight, dataset, and third-party code path has documented public provenance and compatible terms.
- [ ] No company/customer code, data, logs, configuration, screenshots, metrics, or incident text is present.
- [ ] No personal data, precise location data, vehicle identifiers, or re-identifying metadata is present.
- [ ] No credential, key, token, private endpoint, hostname, username, or private path is present.
- [ ] Generated logs/traces/reports were inspected after redaction, including metadata and command lines.
- [ ] Large/binary files are intentional, reviewable, licensed, and necessary.
- [ ] Claims are based only on evidence generated from this repository's public inputs.
- [ ] Uncertain items were omitted pending owner/legal/security review.

## Vulnerability and unsafe-behavior reporting

Do not publish a live credential, exploitable internal detail, or third-party
zero-day as an ordinary issue. Use the affected project's documented private
security-reporting channel. A public reliability experiment should use a safe,
minimal, non-sensitive reproducer.
